BUG 01criticalsecurity You can log in as "admin" with any password at all, because the server only checks that the username exists and never checks the password.

Failing test: “login fails with a wrong password” ui/login.spec.ts:22

Root cause: The POST /api/login handler in src/server.ts looks up the user by username only: `users.find((u) => u.username === username)`. It never compares the password, so any password works for an existing username and the server returns `Welcome, admin!`.

Evidence: The test fills username "admin" and password "wrong-password", then waits for "Invalid username or password". The page showed "Welcome, admin!" instead. The message comes from the server's response (`$("login-message").textContent = data.message`), and in server.ts the only check is `if (user)`. That check only confirms the username exists. Nothing in the handler reads `password`. The test is correct: a login must reject a wrong password. It also waits properly, because toHaveText retries, and the call log shows the message going from empty to the server's reply.

Suggested fix in src/server.ts

current code
  const user = users.find((u) => u.username === username);
suggested fix
  const user = users.find((u) => u.username === username && u.password === password);
BUG 02highsecurity The server accepts 2FA codes up to 10 minutes old, so a code from 5 minutes ago still signs the user in when it should be rejected.

Failing test: “an expired 2FA code is rejected” auth/account.spec.ts:20

Root cause: In src/account.ts, isValidCode() loops `for (let step = -20; step <= 1; step++)`, so it accepts the current 30-second window plus the 20 windows before it. That is about 10 minutes of past codes. The usual RFC 6238 practice is to allow ±1 window for clock drift, which is about 30 seconds either way. A code made 5 minutes ago falls in window now-10, which is inside the accepted range, so the server treats the expired code as valid and starts a session.

Evidence: The test builds a code for Date.now() - 5 minutes, which is window offset -10. The loop checks offsets -20 through +1, so offset -10 matches. The error log shows account-message changing from "Enter the 6-digit code..." to "Signed in as dana", so the server answered verify-code with ok:true and called startSession. The test's expectation is right: an expired one-time code must not log the user in. The code comment says the window covers phone clocks being slightly out of sync, which only justifies a step or so, not 10 minutes.

Suggested fix in src/account.ts

current code
  for (let step = -20; step <= 1; step++) {
suggested fix
  for (let step = -1; step <= 1; step++) {

BUG 04highperformance Each sign-in hashes the password in a way that stalls the whole server, so product browsing slows down for everyone while people log in.

Failing test: “browsing stays fast while many users sign in” load/load.spec.ts:21

Root cause: The /api/account/login route in src/account.ts checks the password with crypto.scryptSync. scrypt is meant to be CPU-expensive, and the Sync version runs on Node's only main thread. While it hashes, no other request can be answered, so 10 users signing in over and over hold up /api/products for everyone else. An async version (promisify(crypto.scrypt)) is already defined in the file but the route never uses it.

Evidence: Browsing during the sign-ins had p50 150 ms, p95 459 ms and max 1188 ms, although /api/products only returns a fixed in-memory array. In src/account.ts the login route calls `crypto.scryptSync(String(password ?? ""), SALT, 64)`, and a comment in the same file says hashing takes "tens of milliseconds of CPU per sign-in". `const scrypt = promisify(crypto.scrypt)` is declared and never used. The load test without sign-ins (30 users, p95 under 300 ms) is not the one failing, so the products endpoint is fast on its own.

Suggested fix in src/account.ts

current code
    const attempt = crypto.scryptSync(String(password ?? ""), SALT, 64);
suggested fix
    const attempt = await scrypt(String(password ?? ""), SALT, 64);
BUG 05highsecurity The server allows 50 wrong 2FA codes before blocking instead of 5, so attackers can brute-force the 6-digit code far more easily than intended.

Failing test: “2FA code guessing is blocked after 5 wrong codes” security/security.spec.ts:31

Root cause: MAX_CODE_ATTEMPTS in src/account.ts is set to 50. The verify-code route only returns 429 when wrongCodes >= MAX_CODE_ATTEMPTS, so after 5 wrong codes the 6th attempt is still evaluated and gets 401 instead of being refused.

Evidence: src/account.ts: `const MAX_CODE_ATTEMPTS = 50;` with check `if ((wrongCodes.get(ticket) ?? 0) >= MAX_CODE_ATTEMPTS) { ... res.status(429) ... }`. After 5 failures the count is 5, and 5 >= 50 is false, so the request falls through to isValidCode and gets 401 'Invalid code'. That matches the error 'Expected: 429, Received: 401'. Related: isValidCode also accepts 22 time windows (step -20..1), which further weakens brute-force protection.

Suggested fix in src/account.ts

current code
const MAX_CODE_ATTEMPTS = 50;
suggested fix
const MAX_CODE_ATTEMPTS = 5;
