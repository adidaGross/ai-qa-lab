When a test fails, is the app wrong or the test?

I've worked in QA for over nine years. I've tested web, mobile and desktop apps, by hand and with automation, built QA processes where there were none, and led QA and support teams. In my last role I also set up Jira Service Management and built two AI support agents with Claude and MCP.

In every team I've led, we lost hours after test runs on the same question: is this a real bug, or did the test break? This project is my attempt to hand that question to an AI. I also wanted to check its answers against an answer key instead of taking its word for it.

01 What I built

  • A small online shop, with bugs I planted on purpose.
  • A Playwright test suite for it, with some tests I broke on purpose.
  • After each run, the AI looks at every failing test, its error and the shop's code, and says which one is at fault.
  • For a real bug, it suggests a code fix. For a broken test, it writes a fixed copy, and that copy is run again to see if it really passes.
  • An answer key, which the AI never sees, grades every answer.

04 What the tests cover

ui + apiproducts, search, cart, discounts, checkout, and the product API
sign-inpassword with a 2FA code, passkeys, saved sessions. The tests generate the 2FA codes themselves and use Chromium's virtual authenticator in place of a real passkey device.
securityXSS, security headers, cookie flags, access control, 2FA brute force, and error messages that give away too much
loadmany users at the same time, with limits on response time and error rate. Each load test starts its own copy of the server, so they don't affect each other.
platformsCI runs everything on Linux, macOS and Windows. npm run setup takes a fresh clone to a working setup in about a minute.

05 Bugs I didn't plant

These weren't part of the plan. They came up while I was building, and each one changed how the project works.

FINDING-01flaky test

A test that only failed on slow machines

The first time CI ran on macOS and Windows, a test I had broken on purpose passed there. It read the page before the server answered, and on fast machines the server happened to win. I changed the login to respond the way a real server does, so timing no longer decides the result.

found by: CI on 3 systems
FINDING-02masked bug

A new feature hid an old bug

Once I added the account page, getByLabel("Password") started finding its new password field, so the test no longer noticed that the old field had no label. The test now points at the exact field.

found by: the baseline check
FINDING-03privacy

A security test that leaked

The test that checks error messages for server paths printed the whole response when it failed, which put a local folder path into the test report. Now it only says that something leaked, not what.

found by: reviewing the report before publishing
FINDING-04tooling

The repair tool tripped on an apostrophe

The code that pulls a single test out of its file got confused by the apostrophe in field's inside a comment, and later by a regex. CI now checks that every failing test can be found in its file.

found by: the AI flow failing at step 3

06 How reliable is it?

A few planted bugs don't prove much, so I wrote a generator that makes new cases. It starts from a clean copy where every test passes. Each mutant adds one small change, either to the app (so the right answer is “app bug”) or to a test (“test bug”). The tests run against every mutant, and the AI judges each failure without seeing the answer. On the hard level, each change is made to look like the other kind of problem.

07 How I approached it

The choices I'd make on a real team, too.

measure itAn answer key and the mutation benchmark turn “the AI seems right” into numbers I can check.
fixed formatThe AI has to answer in a fixed JSON format, checked with Zod. A bad answer fails loudly instead of slipping into the report.
people decideFixed tests go to a separate folder for review. The AI never rewrites the real test suite.
prove the fixA fixed test only counts if it passes when run again.
safe outputAll text in the report is escaped, so it can't have the XSS bug the project tests for. Keys stay in a git-ignored file.
costEvery AI run prints what it would cost, and the fixed part of the prompt is cached to keep that down.

The AI part lives in a separate private package, Faultwise, which I'm also developing. This repo installs it like any other dependency. Without access you can still clone the repo, run all the tests and build this site.
