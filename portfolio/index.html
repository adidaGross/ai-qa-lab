When a test fails, is the app wrong or the test?

I've worked in software quality for over nine years: manual and automated testing for web, mobile and desktop apps, building QA processes from scratch, and leading QA and support teams. In my last role I set up Jira Service Management and built two AI support agents with Claude and MCP. In every team I've led, the same question took hours after each test run: is this a real bug, or is the test broken? I built AI QA Lab to see how well an AI can answer that question, and to measure it instead of trusting it.

01 Setup

  • A small online shop with bugs planted on purpose.
  • A test suite with tests broken on purpose.
  • After every run, the AI reads each failing test, the error and the shop's code, and decides who is at fault.
  • Real bug: it suggests the code fix. Broken test: it writes a corrected copy, which is run again to prove it.
  • An answer key the AI never sees grades every verdict.

05 Found while building

Not planted. These turned up on their own.

FINDING-01flaky test

A test that only failed on slow machines

When CI first ran on macOS and Windows, one deliberately broken test passed there. It read the page before the server answered, and on fast machines the server won the race. The fix: the login now responds like a real server.

found by: CI on 3 systems
FINDING-02masked bug

A new feature hid an old bug

After the account page was added, getByLabel("Password") found the new password field and stopped noticing that the old one had no label. The test now checks the exact field.

found by: the baseline check
FINDING-03privacy

A security test that leaked

The test that checks error messages don't reveal server paths printed the whole response when it failed, copying a local folder path into the test report. It now reports only that something leaked.

found by: reviewing the report before publishing
FINDING-04tooling

The repair tool tripped on an apostrophe

The code that cuts a test out of its file got confused by field's in a comment, and later by a regex. CI now checks that every failing test can be found.

found by: the AI flow failing at step 3

06 How reliable is it?

A handful of planted bugs proves little, so a benchmark generates cases. From a clean copy where every test passes, each mutant adds one small change, to the app (answer: “app bug”) or to a test (“test bug”). The tests run on every mutant, and the AI judges every failure without knowing the answer. The hard level uses changes designed to look like the other kind of problem.

07 The product: Faultwise

The AI part is now its own product, Faultwise. This project installs it as a package and uses it, the way a customer would.

readsPlaywright JSON and JUnit XML, which almost every framework writes: pytest, JUnit/TestNG, Jest, Cypress, Appium, Espresso, .NET, Go. So web, mobile, desktop and server tests.
runs asa command line tool, or a GitHub Action that puts the report on the run's page
any AIClaude, a local model through Ollama for code that can't leave the company, or any OpenAI-compatible service
nextbuilt to grow: Triage and Heal today; flaky tests, CI and deployment failures, and incidents next
